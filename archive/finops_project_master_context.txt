1. PROJECT TITLE
============================================================

Autonomous Cloud FinOps Remediation Agent

============================================================
2. PROJECT SUMMARY
============================================================

The Autonomous Cloud FinOps Remediation Agent is a policy-driven cloud-cost optimization and governance application. It analyzes structured AWS and Azure resource telemetry, utilization metrics, billing information, attachment states, lifecycle data, and ownership tags to identify cloud waste.

The system detects conditions such as idle compute instances, unattached storage volumes, legacy snapshots, unassociated public IP addresses, oversized resources, and missing governance tags. A deterministic Python state machine applies version-controlled FinOps policies and selects a safe recommendation such as DOWNSIZE, ARCHIVE, TERMINATE, NO_ACTION, or REVIEW_REQUIRED.

The project generates reviewable Infrastructure-as-Code remediation artifacts using Jinja2 and Terraform. It validates generated Terraform with Terraform CLI, TFLint, and Checkov before presenting it for human approval. The initial implementation is dry-run and plan-only. It must never execute destructive cloud changes autonomously.

A local Ollama model may convert validated technical findings into concise incident summaries. The LLM is not permitted to decide remediation actions, calculate authoritative savings, modify policy outcomes, execute commands, or bypass safety controls.

============================================================
3. PROBLEM STATEMENT
============================================================

Organizations lose cloud budget to resources that remain active after testing, including idle virtual machines, unattached disks, old snapshots, unassociated public IP addresses, and oversized compute or database services. Manual identification and cleanup are repetitive, inconsistent, difficult to audit, and potentially unsafe.

An automated FinOps system must identify cost waste while protecting production, critical, legally retained, recently created, or explicitly exempted resources. Every recommendation must be explainable, policy-backed, auditable, and reviewable before execution.

============================================================
4. PROJECT OBJECTIVES
============================================================

1. Ingest structured AWS and Azure telemetry from JSON and CSV files.
2. Validate every input record with strict Pydantic schemas.
3. Normalize provider-specific telemetry into a common resource model.
4. Analyze utilization, attachment state, age, tags, ownership, and monthly cost.
5. Load version-controlled FinOps policies from YAML or JSON.
6. Detect cloud waste using deterministic and explainable rules.
7. Protect production, critical, exempted, unknown, and insufficiently observed resources.
8. Select one controlled outcome: DOWNSIZE, ARCHIVE, TERMINATE, NO_ACTION, or REVIEW_REQUIRED.
9. Estimate monthly and annual savings using transparent formulas.
10. Generate Terraform or cloud CLI remediation artifacts through approved templates.
11. Validate Terraform with terraform fmt, terraform validate, TFLint, Checkov, and terraform plan where applicable.
12. Produce Slack-, Teams-, email-, or dashboard-ready incident summaries.
13. Store run history, findings, validation results, approvals, and estimated savings.
14. Run safety, unit, integration, policy-drift, and regression tests in CI/CD.
15. Package the agent for repeatable scheduled execution using Docker.
16. Keep remediation execution disabled until a separate approved production phase.

6. CORE ARCHITECTURE
============================================================

Agent Core:
- Python state machine
- Deterministic Observe, Analyze, Decide, Generate, Validate, and Report transitions
- Idempotent run identifiers
- Controlled retry and timeout behavior
- No autonomous destructive execution

Telemetry Input:
- JSON and CSV files during development
- Synthetic AWS and Azure resource and billing records
- Optional live AWS and Azure SDK connectors in a later phase
- Quarantine malformed or incomplete records instead of guessing values

Validation and Analysis:
- Pydantic for schemas and field validation
- Pandas and NumPy for tabular filtering, aggregation, trends, and savings calculations
- PyArrow for efficient columnar data if needed
- Explicit timezone handling for resource age and observation windows

Policy Engine:
- Version-controlled YAML/JSON policies
- Business rules separated from application code
- Policies specify thresholds, observation periods, actions, exclusions, severity, approval requirements, and calculation methods
- Default-deny behavior for destructive actions

Safety Engine:
- Production and critical tag protection
- Environment allow-list and deny-list
- Minimum observation period
- Missing-owner and unknown-environment escalation
- Maximum findings/remediations per run
- Legal-hold and exemption support
- Human approval for all material actions
- Dry-run by default

Remediation Compiler:
- Jinja2 templates
- Terraform .tf generation
- Optional cloud CLI command generation for review only
- Templates are parameterized, versioned, tested, and allow-listed

Infrastructure-as-Code Validation:

- terraform init with controlled provider access
- terraform validate
- TFLint
- Checkov in a separate environment or standalone binary
- terraform plan when credentials and providers are approved

Summary Engine:

- Larger model is unnecessary for deterministic decisions
- The LLM only summarizes already validated structured results
- Low temperature and Pydantic-validated summary schema

Persistence:
- SQLite for a local single-instance demonstration

- PostgreSQL recommended for multi-instance production
- Store audit history, decisions, policies, artifacts, scans, approvals, and estimated savings

API and Operations:

Observability:

- Correlation/run IDs

============================================================
7. DETERMINISTIC DECISION MODEL
============================================================

The policy engine, not the LLM, selects the outcome.

Allowed recommendation values:
- DOWNSIZE
- ARCHIVE
- TERMINATE
- NO_ACTION
- REVIEW_REQUIRED

Recommended initial behavior:
- Idle compute: DOWNSIZE or REVIEW_REQUIRED
- Unattached storage: ARCHIVE or REVIEW_REQUIRED
- Legacy unreferenced snapshot: ARCHIVE
- Unassociated public IP: REVIEW_REQUIRED or RELEASE recommendation
- Oversized database: DOWNSIZE or REVIEW_REQUIRED
- Production/critical resource: NO_ACTION or REVIEW_REQUIRED
- Missing owner/environment: REVIEW_REQUIRED
- Insufficient observation history: NO_ACTION or REVIEW_REQUIRED

TERMINATE should be rare and must always require explicit human approval. The first project version should generate plans and recommendations only.

Decision precedence:
1. Invalid or incomplete telemetry -> REVIEW_REQUIRED
2. Protected, production, critical, legal-hold, or exempt resource -> NO_ACTION/REVIEW_REQUIRED
3. Insufficient observation period -> NO_ACTION
4. Policy condition not met -> NO_ACTION
5. Policy condition met but ownership/impact uncertain -> REVIEW_REQUIRED
6. Policy condition met with clear non-production evidence -> approved recommendation

23. PRODUCTION SAFETY REQUIREMENTS
============================================================

- DRY_RUN defaults to true.
- ALLOW_REMEDIATION_EXECUTION defaults to false.
- Human approval is mandatory for all material actions.
- Discovery and remediation identities must be separate.
- Discovery identity should be read-only.
- Remediation identity must be least-privilege and short-lived.
- Prefer workload identity, OIDC, or managed identity over static keys.
- Production, critical, legal-hold, and exempt resources must be protected.
- Unknown or conflicting tags must cause REVIEW_REQUIRED.
- Missing owner information must cause REVIEW_REQUIRED.
- Enforce a minimum observation period.
- Enforce maximum actions per run and concurrency locks.
- Use idempotency keys to prevent duplicate actions.
- Preserve evidence and policy versions for every decision.
- Do not let the LLM choose, alter, or execute remediation actions.
- Do not execute strings generated by the LLM.
- Use allow-listed Jinja2 templates with strict parameter validation.
- Run Terraform formatting, validation, linting, policy scanning, and plan review.
- Pin Terraform providers/modules and container images.
- Store reviewed plan artifacts and checksums.
- Redact account IDs, subscription IDs, owner data, and costs where required in notifications.
- Prevent secrets from entering logs, Terraform output, state, plans, or reports.
- Encrypt stored telemetry, plans, findings, and audit records.
- Define retention and secure-deletion policies.
- Add rollback, incident, exception, and emergency-stop procedures.
- Integrate with enterprise change management before any production execution.

- Estimated savings are projections, not guaranteed financial results.
